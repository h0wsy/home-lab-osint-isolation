## Контекст и мотивация

Недавно я задумался над чистотой своей рабочей машины. Безусловно, любую ОС можно держать в чистоте, но я давно подумывал о том, чтобы попробовать нечто новое, поэтому решился на переход с Windows 10 на Void Linux. 

Перед переходом я изучил различные аспекты дистрибутива, принял его недостатки (подробнее об этом я расскажу в своём мини-обзоре, где отмечу конкретные плюсы и минусы) и всё же поставил на рабочую машину. Конкретно в этом кейсе я расскажу, как изолировал свой рабочий стек (OSINT-инструменты) с помощью виртуализации, и заодно познакомился с особенностями виртуализации на Linux-системах.

## Архитектура лаборатории

* **Хост (Host):** Void Linux (агрессивные правила фаервола, маршрутизация через sing-box)
* **Гипервизор:** QEMU/KVM + virt-manager (нативная аппаратная виртуализация)
* **Гостевая ОС (Guest):** Debian (headless / без GUI)
* **Контейнеризация:** Docker
* **Сервисы:** Flowsint, Spyderfoot (OSINT-инструменты)

## Сетевая безопасность и фаервол (nftables)

Изоляция ВМ не имеет смысла без грамотной настройки сети на хосте. На Void Linux используется `nftables` со строгой политикой по умолчанию. 

Основные правила фильтрации на хосте (`table inet filter`):

```text
table inet filter {
	chain input {
		type filter hook input priority filter; policy drop;
		ct state established,related accept
		iif "lo" accept
		iifname "singbox-tun0" accept
	}
}
```

* **policy drop:** Весь входящий трафик по умолчанию блокируется.
* **ct state established,related accept:** Разрешены только ответы на запросы, инициированные изнутри.
* **iifname "singbox-tun0" accept:** Исключение сделано только для интерфейса VPN-туннеля (sing-box).

Для обеспечения связи с виртуальной машиной используется встроенный бридж Libvirt (`virbr0`) с сетью `192.168.xxx.0/24`. Libvirt автоматически генерирует правила в таблицах `ip libvirt_network` и `ip6 libvirt_network`, которые настраивают NAT (masquerade) для выхода ВМ в интернет и разрешают форвардинг между интерфейсами.

## Реализация и доступ к сервисам

1. Развернута виртуальная машина Debian в QEMU/KVM с использованием сети Libvirt по умолчанию (`virbr0`).
2. Внутри ВМ установлен Docker и запущены контейнеры Flowsint и Spyderfoot.
3. **Организация доступа:** Так как на хосте настроен строгий фаервол (блокировка всего входящего трафика, кроме sing-box), прямой доступ к веб-интерфейсу ВМ из внешней сети невозможен.
4. **Решение:** Доступ к веб-интерфейсам инструментов осуществляется через SSH-туннелирование (проброс портов по SSH на localhost хоста) либо через прямой ввод локального IP-адреса ВМ (`192.168.122.x`) изнутри хоста, так как хост является шлюзом для этой сети.

## Практические результаты

В рамках проекта был получен практический опыт:

* Работы с гипервизором QEMU/KVM и утилитой virt-manager
* Настройки сетевого взаимодействия между хостом и виртуальной машиной (SSH-туннели, работа с NAT в Libvirt)
* Развертывания контейнеров Docker внутри изолированной среды
* Настройки безопасности (аудит и понимание правил nftables, изоляция сервисов от основной ОС)

## Выводы

Переход на Linux и использование KVM позволили получить гибкий контроль над виртуализацией. Изоляция OSINT-инструментов в отдельной ВМ с Debian позволяет держать основную систему в чистоте и минимизирует риски при работе с недоверенным софтом. Жесткая настройка фаервола на хосте гарантирует, что даже при компрометации инструментов внутри ВМ, злоумышленник не получит прямого доступа к основной системе или локальной сети.
